    테넌트와 조직

    테넌트와 조직 한눈에 보기¶

    • 테넌트(Tenant): AgenticCP에서 하나의 조직에 대응되는 클라우드 리소스의 논리적 집합체
    • 조직(Organization): AgenticCP에서 하나의 고객 단위(회사, 기관, 팀 등)를 표현하는 사용자 집합
    • 핵심 규칙: 이 프로젝트에서는 1 조직 = 1 테넌트 (1:1 고정 매핑) 을 전제로 설계한다.

    테넌트(Tenant)¶

    TL;DR¶

    • AgenticCP가 하나의 고객/조직 단위로 분리·관리하는 클라우드 리소스의 논리적 컨테이너
    • 네트워크, 보안, 데이터, 과금이 다른 테넌트와 격리된 단위

    개념 정의¶

    테넌트는 AgenticCP에서 하나의 고객 또는 조직이 사용하는 클라우드 리소스, 계정, 정책, 비용 정보의 집합체를 의미한다.
    멀티 테넌트 아키텍처에서 각 테넌트는 서로의 데이터와 리소스에 영향을 주지 않도록 논리적으로 격리된 실행·관리 경계를 형성한다.

    설계 의도 / 등장 배경¶

    • 멀티 클라우드 환경에서도 고객/조직 단위로 리소스와 정책을 분리하기 위해 도입된 개념
    • 보안·과금·운영 책임을 명확히 하기 위해,
      “이 설정·비용·정책이 어느 집단에게 속하는지”를 표현하는 경계로 사용
    • 내부 구현에서는 테넌트라는 기술 용어를 사용하지만,
      비즈니스·고객 커뮤니케이션에서는 “조직(Organization)” 용어를 우선 사용한다.

    주요 특성¶

    • 리소스 격리 단위
    • 각 테넌트는 자체적인 클라우드 프로바이더 설정, 네트워크, 보안 정책, 데이터 저장소를 가진다.

    • 한 테넌트의 장애나 설정 오류가 다른 테넌트에 직접 영향을 주지 않도록 설계한다.

    • 정책/설정 단위

    • 보안 정책, 비용 한도, 기능 플래그, 플랫폼 설정 등은 기본적으로 테넌트 단위로 관리된다.

    • 동일한 기능이라도 테넌트별로 활성/비활성, 제한 값이 다를 수 있다.

    • 수명주기(Lifecycle) 단위

    • 생성 → 활성화 → 일시정지/만료 → 종료 등의 라이프사이클을 테넌트 단위로 관리한다.
    • 테넌트 상태 변화는 연결된 조직의 서비스 이용 상태를 그대로 반영한다.

    조직(Organization)¶

    TL;DR¶

    • AgenticCP 상에서 하나의 고객 단위(회사, 기관, 팀 등)를 표현하는 사용자 집합
    • 해당 고객에 속한 사용자, 관리자, 권한 체계를 포괄하는 개념

    개념 정의¶

    조직은 AgenticCP 상에서 실제 비즈니스 주체(회사, 기관, 사업부, 팀 등) 를 표현하는 단위이다.
    하나의 조직은 자신만의 사용자 계정, 역할/권한 구조, 내부 팀 구조를 가지며,
    해당 조직이 사용하는 모든 클라우드 리소스는 1:1로 매핑된 테넌트에 속한다.

    주요 특성¶

    • 사용자/권한의 기본 스코프

    • 조직은 해당 고객 소속 사용자들을 묶는 단위이며,
      이 안에서 일반 사용자(User), 관리자(Admin), 조직 내 최고 관리자(Super Admin 등) 가 정의된다.

    • 내부 구조 표현

    • 필요 시 본부/부서/팀 등의 하위 조직 구조를 표현할 수 있지만,
      외부(플랫폼 전역) 관점에서는 “하나의 조직 = 하나의 테넌트” 로 본다.

    • 온보딩/오프보딩 단위

    • 새로운 고객/조직이 등록되면 해당 조직과 1:1로 연결된 테넌트가 함께 생성된다.
    • 조직 해지나 계약 종료 시, 연결된 테넌트도 함께 종료 수순을 밟는다.

    테넌트–조직 관계¶

    1:1 고정 매핑 규칙¶

    • 이 프로젝트의 핵심 전제:

    1 조직 = 1 테넌트
    하나의 조직은 정확히 하나의 테넌트와 매핑되고,
    하나의 테넌트는 정확히 하나의 조직에만 속한다.

    • 구현 관점 예시
    • Organization.id ↔ Tenant.id 또는 Tenant.tenantKey 형태로 직접 매핑
    • 조직/테넌트 조회 시 상대 개념에 대한 참조를 항상 함께 제공하는 것을 권장

    설계상의 이점¶

    • 개념 단순화
    • 고객에게는 “우리 조직 = 우리 테넌트”라는 단순한 모델을 제공

    • 내부적으로는 멀티 테넌트 아키텍처의 장점을 유지하면서도,
      도메인 언어는 조직(Organization) 중심으로 설명할 수 있다.

    • 정책·과금·모니터링 일관성

    • 권한, 보안 정책, 비용, 모니터링, 감사 로그 등 모든 관리 포인트를
      하나의 경계(조직=테넌트) 기준으로 정렬할 수 있다.
